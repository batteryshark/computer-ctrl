# System One decision models for computer use

Research date: 2026-10-13. Primary documentation and source review only; no models installed, API calls measured, GUI experiments or implementation changes. Benchmarks below belong to the cited authors and are not cctl results. This is a recommendation, not an adopted feature or model choice.

## Finding

**An optional fast executor is worth evaluating; making Jev a core dependency is premature.** The useful feature is a short bounded observation/action loop that can finish routine work without returning to the main harness model after every click. A fast model called alongside the main model on every step can add latency instead. Keep the existing toolkit contract, policies and coordinate/reference validation in control; put model training outside this toolkit.

Distinguish three jobs:

| Job | Required input/output | Appropriate mechanism |
|---|---|---|
| Semantic selection | Goal + observed candidate elements/actions → one candidate | Jev, open decision head, text classifier/reranker |
| Pixel grounding | Screenshot + target description → image coordinates | Existing optional `locate` grounder |
| Short task execution | Goal + repeated observations → actions, recovery, stop | Optional executor using selection and/or a visual policy |

These boundaries are architectural inference, not model guarantees. Current cctl has `locate`, fixed `batch` actions and `then=` observations; it has no `delegate` executor. [Contract](../../contract/tools.json), [engine](../../src/cctl/engine.py), [grounding](../../src/cctl/grounding.py). The tracker already treats sidecars as optional and says to keep them only on eval evidence. [.project/tracker.md](../../.project/tracker.md)

## What Jev currently provides

- **Observed public API:** `POST https://api.typesafe.ai/v1/systemone` takes `state` plus independently evaluated typed questions. Choice selects from at most 255 options and returns the full distribution; Score takes 2–10 ordered levels and returns a probability-weighted score; Noul returns a yes probability. Choice/Score also return confidence. This is a bounded decision service, not an action runner. [API reference](https://docs.typesafe.ai/api)
- **Observed modality/model limits:** Jev 1.13.0 accepts text/JSON only, explicitly excluding images, audio and video. It has a 64k total request limit and a 32k state-plus-longest-question limit. Same weights serve all accounts; no customer fine-tuning/LoRA is offered. Use a versioned ID when thresholds depend on it. [Models](https://docs.typesafe.ai/models)
- **Consequence for cctl:** it can choose a fresh DOM/a11y token or an already enumerated action, classify a dialog, or request escalation using OCR/a11y text. It cannot directly see an unlabeled canvas target or generate arbitrary content to type. TypeSafe's function-calling cookbook likewise dispatches enums; free text/numeric/date arguments retain function defaults. [Function calling](https://docs.typesafe.ai/cookbooks/function_calling)
- **Observed caveats:** TypeSafe documents literal reading, unreliable counting/arithmetic/date comparisons, weaker indirection, distraction from large state, option-order bias and adversarial steering. It explicitly discourages generation by chained choices. Typed output therefore prevents malformed or out-of-list output, not a wrong in-list decision. [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

TypeSafe claims a new architecture, parallel sampler and RLCD training; its public SDK/adapter is not a publication of Jev's weights or full training recipe. **Vendor performance claim:** 70–500 ms per call, with launch evals mostly run from West Coast laptops near its service. Its advertised 193.6× speedup comes from particular workflows, uses frontier-model consensus as reference rather than independent ground truth, and compares through a structured-decision LLM wrapper. The company flags these gains as an optimistic end of real-world results. Its Doom demo used structured text game state, not pixels. [TypeSafe launch explanation](https://typesafe.ai/blog/introducing-system-one-models-and-jev), [official LLM adapter](https://github.com/typesafe-ai/system-one-adapter-python)

**Confidence is not a universal probability of correctness.** Jev's Choice confidence is `(p_max - 1/n)/(1 - 1/n)`; its scale changes with option count. Noul has no separate confidence field. Docs advise choosing thresholds on one's own domain data. Inference for this project: measure empirical error versus accepted coverage on held-out UI states, separately for action/target/stop decisions; do not interpret `confidence=0.9` as a demonstrated 90% chance of completing the GUI task. [Confidence documentation](https://docs.typesafe.ai/confidence)

## Concrete alternatives and computer-use evidence

**A computer-use specialist already exists in the engine's ecosystem:** Cua-S1 is explicitly a research family with checkpoint-specific task contracts. Its `cua-s1-4b-0.2` has separately trained text and screenshot LoRA adapters, with held-out decision and live GUI reinforcement-learning evidence; the live tasks remain single-widget exercises, not a general desktop benchmark (13 environments; six excluded). The tiny form specialist is more cautionary: Cua's model card reports 29.3% accuracy on a small out-of-catalogue form set, with 36/41 answers being SKIP at mean confidence 0.974. This is a strong candidate to evaluate and strong evidence against trusting confidence without scope/verification checks. [Cua-S1 model card](https://github.com/trycua/cua/blob/main/libs/cua-s1/MODEL_CARD.md)

**OpenAI's alternative is now documented:** the linked October 4 article's claim that no public schema exists is stale. The official reference describes `POST /v1/decisions`, with text/image inputs and bounded classification/scoring output. Image support makes it a possible screenshot-based selector, but the endpoint does not itself execute computer-use tools or establish coordinate-grounding accuracy. Access and actual workload latency still need checking; no request was measured here. [Official Decisions API reference](https://developers.openai.com/api/reference/resources/decisions/methods/create)

| Candidate | Primary evidence | Implication for this project |
|---|---|---|
| **Kev** | Open Qwen-based trained decision family; same `/v1/systemone` API; CUDA/ROCm/MLX serving. Author reports Kev-4B model time 41.5 ms for six short-text questions on L40S, versus 721 ms for five ~270-token questions on an M5. These are different hardware/workloads, not a controlled comparison; GPU timings exclude network. Calibration is temperature fitting and authors warn about option order and distribution shifts. [Repository](https://github.com/jaredpalmer/kev) | Useful local baseline on existing inference hosts; do not import the GPU headline as expected Mac latency. |
| **Laya** | Open encoder-based Choice/Score/Noul model. README states shipped checkpoints are overconfident and base models are near chance on its typed-decisions zero-shot benchmark. Default 512/1024-token question windows and option budgets need attention. It describes itself as a base to specialize. [Repository](https://github.com/NandhaKishorM/laya) | Smaller local baseline, particularly after UI specialization; confidence alone cannot repair missing/truncated candidates. |
| **Laya browser specialist** | `cklxx/laya-browser` v19s picks operation and candidate in one pass from a DOM element table. A separate Qwen writes text. Author reports 22–27 ms with GPU at full clock, 75–270 ms after idle clocks, and only ~20–26% on its harder multi-step tasks on held-out real sites, despite 54/54 on its simpler Suite B. Harness changes contributed to gains. [Model card](https://huggingface.co/cklxx/laya-browser) | Direct evidence that a special fast browser decider is feasible and that easy-task success does not establish robust general task completion. |
| **GLiClass / SetFit / reranker** | GLiClass classifies text against arbitrary label sets in one encoder pass; SetFit trains Sentence Transformer classifiers with few labeled examples; Jina rerankers return query-candidate relevance scores. [GLiClass](https://docs.knowledgator.com/docs/frameworks/gliclass/intro/), [SetFit](https://huggingface.co/docs/setfit/en/index), [Jina model card](https://huggingface.co/jinaai/jina-reranker-v3) | Compare these cheaper mechanisms for narrow intent/dialog classification or candidate shortlisting. Ranking similarity is not calibrated action correctness; none supplies pixel grounding by itself. |

**A working Jev browser architecture already exists:** Browser Use's `jev-ultrafast` builds a new indexed element table per observation, asks operation and compatible targets speculatively in one Jev call, executes only the matching target answer, and calls a small LLM for `TYPE_TEXT`. Screenshots are rendered afterward for inspection. Its 7.1-second Flights example is a project demo, not a general browser/desktop benchmark. [Repository](https://github.com/browser-use/jev-ultrafast)

**Direct research evidence:** the September 24 Jev-Mobile preprint delegates local goals and exact typing content from a low-frequency VLM to Jev, which selects current accessibility-tree action IDs, DONE or BLOCKED. Code rebuilds candidates after every action; missing visual targets remain unreachable. Authors report 79% success on full AndroidWorld versus 84% for step-wise VLM. Among successful trajectories, mean time fell 32.7% and mean all-model API cost fell 73.4%. These compare complete mobile systems with different execution interfaces, and the paper lacks a small-VLM replacement inside the same delegated controller. This supports the architectural experiment without proving a pure Jev effect or desktop benefit. [Jev-Mobile preprint](https://arxiv.org/html/2609.30186)

The user's [JevBench link](https://benchmarkheaven.com/jev-models) evaluates bounded decisions and rubric outputs, not successful desktop workflows. Main-page direct retrieval exceeded the web tool's size limit; its indexed description and an accessible [individual system methodology](https://benchmarkheaven.com/jev-models/jevk5-v02) establish that local timings are GPU/loopback while hosted APIs include network. Ranking uses `2 × measured p50 + 150 ms` as an assumed network adjustment for local models. Use it to discover candidates, then evaluate the exact toolkit workload.

## Proposed integration and test

A possible future seam is `delegate(goal, success_condition, max_steps, allowed_actions)` backed by a swappable sidecar. This is a proposal, not the current contract. The main model defines the goal and constraints; executor code owns observation, candidates, reference freshness, allowed actions, budgets and final verification. Prefer DOM/a11y candidates; use `locate` or a visual policy only when needed. Include `none/unknown`, `wait`, `done` and `escalate` as explicit outcomes. Supply typed content from the caller or a separate text model. Validate a complete selected action in code: independently valid operation and target can still form an invalid pair.

Start with browser forms and native dialogs. Compare deterministic matching/batching, host-model-only, hosted Jev, one local decision head, and an applicable specialist. Record end-to-end completion time, p50/p95 per-step latency, task success, incorrect actions, false DONE, recovery and escalation rates. Include missing/duplicate targets, reordered candidates, hidden elements, stale refs, popups, loading states and held-out applications. Fit thresholds on one split and lock them before the held-out evaluation. Keep deterministic success checks when available; a model's DONE/confidence is evidence, not verification.

Run through at least two harnesses per AGENTS.md, on the existing inference host rather than assuming models belong on the VM. Adopt only if task-level speed improves with acceptable error/coverage and without regression on held-out tasks. No acceptance test ran in this research session.
