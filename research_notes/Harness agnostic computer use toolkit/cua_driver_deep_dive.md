## 1. Cua Driver: exact tool surface (v0.34.0)

### Takeaway
`cua-driver mcp` serves **64 tools** in 0.34.0:
- 59 on macOS, Linux and Windows
- 4 Linux-only: `mouse_button_down`, `mouse_button_up`, `mouse_drag`, `parallel_mouse_drag`
- 1 Windows-only: `debug_window_info`

Nightly macOS builds add 2 more (`history_status`, `history_query`). There is no standalone `screenshot` tool. Window screenshots come from `get_window_state` and full-display screenshots from `get_desktop_state`. Every tool is also callable as `cua-driver call <tool> '<json>'` through the daemon.

### Inferences
- The surface is large and stateful: snapshots, tokens, sessions and capture IDs. One toolkit could expose a much smaller, opinionated subset (observe / zoom / act / batch / browser) and route to Cua's `call_tool` underneath. Cua already worries about schema cost: it publishes an external `cua-mcp-filter` script, not a built-in tool filter.
- Exact parameter names drift between platforms (`[l]`/`[m]`/`[w]` above) and between releases. A wrapper that pins the version and normalizes schemas would shield harnesses from that churn.

### Gaps
- The hosted reference tables omit some parameters that the contract manifest and tool descriptions mention, such as `tree_format`, `since`, `full_output` and `verbose` on the macOS `get_window_state` table. I did not run `cua-driver list-tools` or `describe` to get the live JSON schemas, so treat the per-platform parameter lists as docs-derived.

## 2. Cua Driver: architecture

### Takeaway
Cua Driver is a roughly 368k-line Rust workspace of 16 crates, with three per-OS platform crates behind a shared `cua-driver-core`. It implements MCP itself; it does not use rmcp or any MCP SDK. It speaks modern MCP **2026-07-28** over stdio and still accepts legacy `initialize` on **2025-06-18**. Its daemon protocol is newline-delimited JSON over a Unix socket or Windows named pipe. A UniFFI SDK (Python/TypeScript) can embed the same runtime in-process.

### Cited Findings
- Workspace members:
  - `cua-driver` (the binary/daemon)
  - `cua-driver-core`, `cua-driver-contract`, `cua-driver-sdk` (UniFFI), `cua-driver-bindgen`
  - `cua-driver-testkit`, `cua-driver-e2e`
  - `cua-driver-uia` (Windows uiAccess worker)
  - `platform-macos`, `platform-windows`, `platform-linux`
  - `cursor-overlay`, `cua-cursor-motion`, `cursor-theme-cli`, `pip-preview`
  - `cua-perception`

  - PyPI `cua-driver` 0.34.0, MIT, 53 releases. — [PyPI JSON](https://pypi.org/pypi/cua-driver/json)

- macOS process identity constrains how a wrapper or gateway may connect.
  - The embedding guide says registering `cua-driver serve --embedded` from "a gateway, daemon, or Node process that spawns MCP servers… makes the daemon inherit the gateway's identity, not the app's". It also says "gateways may connect an MCP proxy to the app-owned private socket."
  - The README says "Directly spawning a raw `cua-driver serve` outside `CuaDriver.app` without embedded mode is unsupported".
  
  — [Skills/cua-driver/EMBEDDING.md](https://github.com/trycua/cua/blob/b0a6348133a34b3d158eae38d06a606215eec6df/libs/cua-driver/rust/Skills/cua-driver/EMBEDDING.md); [libs/cua-driver/README.md](https://github.com/trycua/cua/blob/b0a6348133a34b3d158eae38d06a606215eec6df/libs/cua-driver/README.md)

### Inferences
- The in-process SDK `create()` + `call_tool()` is the cleanest no-fork extension seam. A wrapper process (Python, TS, or Rust via git dependency) can host the Cua runtime, expose its own MCP server, and add tools Cua lacks: audio, clips, OCR and policy wrapping. It inherits Cua's permission ceiling via `create_configured`.
- On macOS, a wrapper should therefore use SDK `connect(socket_path)` to the `CuaDriver.app` daemon, or proxy `cua-driver mcp`, rather than `create()` in-process. Otherwise TCC grants attach to the harness or terminal. On Linux and Windows, in-process `create()` or a child `cua-driver mcp` are both fine.
- Because the MCP layer is hand-rolled and has no progress notifications, long-running tools such as an N-second clip recorder should stay under harness timeouts, or be split into start/stop pairs. This matches the Tasks/MRTR notes in `harness_integration.md`.

### Gaps
- I did not verify the exact UniFFI SDK method list for Python vs TypeScript, beyond the docs table.
- I did not confirm whether the SDK can be consumed from Rust as a library without vendoring. It is not on crates.io, so a git dependency would be needed.

## 3. Cua Driver: screenshots, scaling, zoom, accessibility and element tokens

### Takeaway
Screenshots return as MCP `image` content (base64 PNG) plus `structuredContent`. They can instead go to disk via `screenshot_out_file`, or via `--screenshot-out-file` on the CLI.
- **Window captures** default to ≤1568 px on the long edge (about 1.15 MP), with automatic coordinate mapping.
- **Desktop captures** are full-size unless capped.
- **`zoom`** is window-scoped only. It returns a JPEG of a region at most 500 px wide with 20% padding, and `from_zoom=true` maps clicks back.
- **Accessibility:**
  - Platform APIs: AX on macOS, UIA with a CacheRequest batch walk on Windows, AT-SPI over D-Bus on Linux.
  - The tree is rendered as compact Markdown with `[N]` rows and element tokens `s%08x:N`.
  - Walks are bounded to 250 nodes by default, with diff reads via `since`.

A multimodal harness interprets the image; Cua Driver does not OCR it or assign task meaning." ### Inferences
- Cua's screenshot/zoom semantics are window-first. For "look at the whole screen, then zoom into a region", the user gets `get_desktop_state` (full-res by default, which is expensive) but no desktop `zoom`. A wrapper should add a desktop-region crop/zoom tool and default `max_image_dimension` for desktop captures.
- The token-and-snapshot discipline (stale tokens, `screenshot_context_missing`, sessions) is robust but unforgiving for one-shot CLI use. Every `cua-driver call` gets a disposable session unless a `session` label is repeated. Harness skills must teach that.

### Gaps
- I did not live-test the actual default image size returned by `get_desktop_state` on a 4K display, or token cost per call.

## 4. Cua Driver: browser (CDP), recording/video, audio, processes

### Takeaway
**Browser.** The `browser_*` tools use CDP over websockets, bound to an exact native `(pid, window_id)`. They produce `semantic_v2` snapshots with refs like `p1:7`.
- They can launch a driver-owned isolated Chromium profile.
- Attaching to a logged-in profile needs an explicit launch-time grant.
- Trusted background pointer input works only on Windows. macOS and Linux refuse it, or fall back to `input_route:"dom_event"`, which is unverifiable.

**Recording.** Recording is a per-action *trajectory* recorder (before/after PNG + JSON per action). With `record_video:true` it also writes a whole-session main-display `recording.mp4`:
- H.264 at 30 fps.
- macOS uses ScreenCaptureKit. Windows and Linux use ffmpeg `gdigrab`/`x11grab`.
- `stop_recording` returns a file path.

There is **no clip-on-demand tool and no audio capture anywhere in the driver**.

**Processes.** `list_apps` and `kill_app` cover processes. Standard mode refuses to kill processes the runtime did not launch.

### Cited Findings
- Browser architecture — [browsers.mdx](https://github.com/trycua/cua/blob/b0a6348133a34b3d158eae38d06a606215eec6df/docs/content/docs/cua-driver/guides/browsers.mdx):
  - "The `browser_*` tools act inside Chromium and Electron pages through the Chrome DevTools Protocol (CDP), bound to the exact native window you picked."
  - Safari, Firefox, Tauri, WKWebView, WebKitGTK and split-process WebView2 return `browser_route_unavailable`.
  - The flow is `get_browser_state` → `target_id`/`tab_id` → `snapshot_format:"semantic_v2"` (outline + action `refs` + `content_refs`) → `browser_click`/`browser_type`/`browser_navigate`. "Refs die on a newer snapshot, navigation, or reconnect".

### Inferences
- Short clips for video models can be emulated with `start_recording(record_video:true)` → wait → `stop_recording`. The cost is that every action in that window also writes turn folders. The clip is always the full main display (no window/region), always 30 fps, and is returned as a path, never as content. A dedicated `record_clip(duration_ms, region|window, fps, max_dim, format)` tool is a clean addition. It could be upstream or in a wrapper. The plumbing already exists: the SCK recorder and the ffmpeg subprocess.
- Audio is a full greenfield item. Cua's Linux crate already links `pipewire`/`libspa` (for portal screencast) and its macOS crate links `screencapturekit`. Those are natural hosts for PipeWire monitor capture and SCStream `capturesAudio`. Windows would need WASAPI loopback. None of this exists today.
- The "process listing" goal is met on Linux and Windows through `list_apps`. On macOS it is GUI-apps-only. Full `ps`-style listing would be a wrapper tool.

### Gaps
- I did not verify whether the Windows `list_apps` includes non-GUI processes.
- I did not test whether Cua accepts browser CDP attach to a Chromium started with `--remote-debugging-port` and a non-default `--user-data-dir`. That is the usual agent-browser pattern; the docs say `launch_app` refuses remote-debugging flags.

## 5. Cua Driver: permission model, safety defaults, telemetry, cloud dependencies

### Takeaway
The default mode `standard` is promptless: observe, click, type, record and isolated browsers are all allowed. Hardening is fully opt-in but strong:
- `bounded` mode with a deny-by-default YAML capability manifest (apps by bundle id or absolute executable, file roots, desktop display flag).
- YAML or Rego tool/argument policies.
- Admin-managed policy files.

Telemetry to PostHog EU is **on by default**. Events are pseudonymous and content-free, but they include per-tool completion events and the MCP client name. Opt out with `DO_NOT_TRACK=1`, `CUA_TELEMETRY=0` or `cua-driver telemetry disable`.

A separate update check (GitHub/cua.ai) runs by default. Nothing requires a Cua cloud account.

### Cited Findings
- Authorization layers, each of which "can only narrow" — [permissions.mdx](https://github.com/trycua/cua/blob/b0a6348133a34b3d158eae38d06a606215eec6df/docs/content/docs/cua-driver/guides/permissions.mdx):
  1. Hard invariants
  2. Built-in tool/risk map
  3. `CUA_DRIVER_MANAGED_POLICY_FILE`
  4. `CUA_DRIVER_POLICY_FILE`
  5. Permission mode
  6. Capability manifest
  7. Launch grant / host decision
  
  "an agent cannot change it from a tool call, and a running daemon cannot be reconfigured".
- Modes — [permissions.mdx](https://github.com/trycua/cua/blob/b0a6348133a34b3d158eae38d06a606215eec6df/docs/content/docs/cua-driver/guides/permissions.mdx):

- Outbound endpoints compiled into the driver crates: `eu.i.posthog.com`, `github.com/trycua/cua/releases` (+ `releases.atom`), `raw.githubusercontent.com/…/Skills/cua-driver` (skill pack), and `cua.ai/driver/install.sh`/`.ps1`. ### Inferences
- A "restrictive by default" toolkit needs **no fork** for policy. A wrapper launcher can:
  1. Always start the runtime with `CUA_DRIVER_PERMISSION_MODE=bounded`, a generated manifest and a YAML or Rego policy.
  2. Set `DO_NOT_TRACK=1` and `CUA_DRIVER_RS_UPDATE_CHECK=false`.
  3. Pass `create_configured(options)` when embedding.
  
  Untrusted-content wrapping of returned text (as clawdcursor does) is not in Cua. It would have to live in the wrapper, as post-processing of `content[].text`, or go upstream as an RFC.
- Telemetry on by default, with per-tool events and reported model/agent names, is a policy decision the toolkit must override explicitly. It is easy to do via environment, but must be documented.

## 6. Cua Driver on Linux X11, and driving a Debian 13 XFCE VM over SSH or Tailscale

### Takeaway
**Status.** X11/Xorg is "Supported" (XTest + window-addressed X11 input + AT-SPI). Raw background input is toolkit-dependent.

**Headless over SSH into an existing XFCE session** works with one manual step: **set `DISPLAY` yourself**. The driver then:
- auto-discovers `XAUTHORITY` from the running X server's `-auth` argument in `/proc`;
- auto-discovers `DBUS_SESSION_BUS_ADDRESS` from `/run/user/<uid>/bus` or from `xfce4-session`'s environment.

It does **not** discover `DISPLAY` (open issue #3047).

**Recommended remote shapes:**
- `ssh vm 'DISPLAY=:0 cua-driver mcp'`. On Linux the MCP process owns the runtime.
- A `cua-driver serve` daemon started inside the XFCE session, plus `ssh vm cua-driver mcp --socket ~/.cache/cua-driver/cua-driver.sock`. There is no official systemd user unit (open issue #3957).

**Caveats.** Several open X11 bugs affect reliability: silent `type_text` drops, a title-bar offset, overlay freezes and a UTF-8 truncation.

### Cited Findings
- Support levels — [platform-support.mdx](https://github.com/trycua/cua/blob/b0a6348133a34b3d158eae38d06a606215eec6df/docs/content/docs/cua-driver/concepts/platform-support.mdx):
  - "Linux X11 | X11/EWMH, XTest, AT-SPI | Supported with toolkit limits. Toolkits that reject synthetic background events get an explicit refusal."

### Inferences
- For the user's Debian 13 XFCE/X11 VM, Cua Driver is the strongest off-the-shelf option. The concrete recipe is:
  1. Install via `install.sh` (glibc floor 2.31; Debian 13 has a newer glibc, so it should work, but this is untested in Cua's matrix).
  2. Make sure `libxi6`, `at-spi2-core` and `ffmpeg` are present.
  3. Register `ssh -T user@vm-tailnet-name 'DISPLAY=:0 cua-driver mcp'` as an MCP stdio server in each harness.
  
  SSH or Tailscale SSH supplies authentication, so no new network listener is needed.
- The open X11 reliability bugs (#3774 silent `type_text` loss, #3237 title-bar offset) directly hit the "click and type" loop. Budget time to validate on XFCE/xfwm4 specifically. Cua's CI uses openbox under Xvfb, not xfwm4.
- A wrapper should own the `DISPLAY` discovery the driver lacks: pick `:0`, or parse `loginctl`/`who`/`/proc/*/environ` for the logged-in user's X server. It should also own a systemd `--user` unit for `serve`, closing #3957 locally.

### Gaps
- I did not live-test Cua Driver on Debian 13 / XFCE 4.20 (xfwm4 compositor on or off), on X11 over SSH, or in a VM without GPU. All conclusions are from source and docs.
- I did not determine whether bare `ssh … cua-driver mcp`, which creates a new runtime per MCP connection, interacts badly with a concurrently running `serve` daemon (overlays, MPX pointers).

## 7. Cua Driver: packaging, signing, tests/CI, release cadence, breaking changes, bus factor, issue health, licenses, extensibility

### Takeaway
- **Engineering rigor.** Cua Driver is a mature engineering effort: 3,495 test attributes, release-gating desktop E2E on Linux, Windows and macOS, a nightly fuzzer, signed and notarized macOS builds, Authenticode-signed Windows builds and SHA256-verified installers.
- **Churn.** It is extremely high-churn:
  - 113 tagged releases from 2026-05-13 to 2026-10-05, including 34 in the last 60 days.
  - 9 changelog sections marked BREAKING since 0.11.0 (2026-07-22).
  - The latest break (0.31.0) made element actions token-only and schemas closed.
- **Bus factor.** It is effectively one lead developer, Francesco Bonacci: 72% of non-bot commits to `libs/cua-driver` and 213 of 427 commits in the last 60 days.
- **Licensing.** The driver is MIT, with MIT third-party code. Only the opt-in perception extension carries AGPL (the OmniParser detector); its OCR models are Apache-2.0.

### Inferences
- Churn risk is the top operational risk. Any wrapper must:
  - pin an exact Cua version;
  - run a contract test, e.g. `cua-driver list-tools` JSON snapshot diffing, before bumping;
  - avoid depending on undocumented text output (Cua itself says text is not a stable API).
- The bus factor is low despite the large contributor list. Cua is a VC-backed company (it sells hosted Spaces), so continuity depends on the company, not on community depth.
- An OCR-only, non-AGPL perception artifact is technically possible: the PP-OCRv5 models are Apache-2.0 and the `cua-perception` crate is workspace-MIT. But shipping it through Cua's extension system needs either Cua to publish a split artifact or "developer mode" unsigned installs. A wrapper-side OCR (RapidOCR or PP-OCR via ONNX Runtime, run on the PNGs Cua returns) avoids the extension system entirely.

### Gaps
- I did not run a dependency-license audit (`cargo deny`/`cargo about`) over the 630 crates in `Cargo.lock`, and no `deny.toml` was found in the repo. The notable dependencies I checked by name (x11rb, atspi, zbus, ashpd, pipewire, reis, regorus, windows, objc2, screencapturekit, ort) are permissive to my knowledge. That is not verified per crate here.
- I did not verify the PyPI and npm packages bundle exactly the same binary as the GitHub release. The README says they are "assembled from the same `cua-driver-rs-v*` release artifacts".

## 8. Competitors at source level

### Takeaway
None of the four tool-layer competitors is a credible *cross-platform* foundation, and the fifth (Holo) is not a tool layer at all.

| Project | Shape | Strengths | Limits |
|---|---|---|---|
| **computer-use-linux** | Linux-only Rust/rmcp, 18+2 tools | The best second Linux engine: compositor-aware window registry, session-environment hydration, no telemetry, an explicit XFCE/EWMH backend, Claude/Codex plugins and a native pi package | No OCR, browser, recording or audio; no live-desktop CI |
| **clawdcursor** | TS, 100 granular tools, or 7 compound tools with `--compact` | The richest safety and perception *ideas*: fused a11y+OCR `el_N` IDs, `<untrusted-screen-content>` tags, tiered gate, key blocklist, `expect` postconditions | Heavy stack (Node, Playwright, sharp/LGPL libvips, Python, Tesseract); solo-maintained |
| **Open Computer Use** | A faithful 9-tool Codex surface on macOS/Windows/Linux | The best `/proc` session-environment discovery (xfce4-session ranked) | Thin Linux backend (python3 per call); no safety layer; a full snapshot after every action (context bloat); no PR CI |

| **Holo Desktop CLI** | One MCP tool, `holo_desktop(task)`, over a closed `hai-agent-runtime` | — | Not a reusable tool layer |

## 9. Decision: is any candidate clearly the best foundation, and what must be added to Cua Driver?

### Takeaway
**Cua Driver is clearly the best foundation.** None of the four competitors combines every required OS with a11y, background input, a CDP browser, zoom, recording, a policy engine, harness presets and release-gated desktop E2E.

**Recommended route: build on it as a pinned dependency behind a thin, owned wrapper layer.** Do not fork it, and do not build fresh.
- **Upstream:** only small, uncontroversial fixes, such as `DISPLAY` discovery (#3047), a Linux systemd unit (#3957) and the stale pi preset.
- **Wrapper:** the new modalities (audio, on-demand clips, MIT/Apache OCR, desktop zoom), the restrictive default profile, untrusted-content tagging, transport, and per-harness packaging.

A fork is the fallback only if Cua refuses to expose a needed hook. At about 0.75 releases/day, 9 breaking release sections in 11 weeks and a 368k-line Rust tree, a fork would diverge within weeks.

### Inferences
- **Recommendation: build on Cua Driver, and add a thin harness-agnostic layer (the "toolkit") that you own.**
  - Process topology:
    - **Linux/Windows:** the toolkit's MCP server holds a child `cua-driver mcp` (or SDK `create()`) on the target machine.
    - **macOS:** it holds an SDK `connect()` to the `CuaDriver.app` daemon socket.
    - **Remote VM:** the harness runs `ssh -T user@vm 'toolkit mcp'`, or `tailscale ssh …`, and the toolkit spawns Cua locally on the VM with a discovered `DISPLAY`.
  - Tool surface: a curated subset of Cua tools, passed through with normalized schemas, plus the toolkit's own tools:
    - `record_clip`
    - `capture_audio` (start/stop and fixed-duration forms)
    - `ocr(region|capture)`, using PP-OCRv5 or RapidOCR ONNX, Apache-2.0
    - `desktop_zoom`
    - `ps`
    - `doctor`, covering DISPLAY, AT-SPI, ffmpeg and audio devices
  - Policy: launch Cua in `bounded` mode with a generated manifest plus YAML/Rego policy, and set `DO_NOT_TRACK=1` and `CUA_DRIVER_RS_UPDATE_CHECK=false`. Wrap every text result from screen, a11y or OCR in an untrusted-content tag.
  - Packaging: a Claude Code plugin (`bin/` + `.mcp.json` + skill), a Codex plugin/config, an opencode `mcp` entry + skill, and a pi package. The pi package should be a native extension that returns images, or use pi 1.0 MCP with `exposure: direct`. All of them point at one binary and one SKILL.md.
- **Upstream contributions:** only small, high-acceptance items:
  - #3047 DISPLAY discovery; the Open Computer Use `/proc` scan is a proven pattern.
  - A Linux systemd user unit (#3957).
  - Fixing the stale `--client pi` preset.
  - Optionally, a desktop-scope `zoom` and a `record_clip` tool via RFC.
  
  Audio is a new modality and a new permission surface (microphone and system-audio privacy). Under Cua's RFC process it would be slow, and it might be declined as out of scope. Keep it in the wrapper.
- **Why not fork:** a fork would have to re-absorb weekly breaking refactors of a 368k-line, single-lead codebase. The wrapper only depends on the documented MCP/SDK boundary (pin the version and snapshot `list-tools`), which Cua explicitly treats as its stable contract ("MCP remains implemented by the `cua-driver` executable as the runtime-neutral agent boundary").
- **Why not build fresh:** the Linux-only goal (Debian XFCE) could be met fresh in weeks by borrowing computer-use-linux and Open Computer Use ideas. But Windows UIA background input, macOS AX/SkyLight/ScreenCaptureKit with TCC identity, a CDP browser bound to native windows, and the Wayland compositor matrix together represent months of work that Cua has already verified with release-gated E2E. Fresh only makes sense if Cua's licensing or direction changes. It is MIT now, so a future relicense would not retroactively affect pinned versions.
- **Hedge:** define the toolkit's own tool schema as the public contract, with Cua as the default "engine". Then a Linux engine adapter for computer-use-linux could be swapped in if Cua's X11 bugs (#3774, #3237) are not fixed. Both speak MCP stdio with image content, so the adapter is a mapping layer.
- **Audio backends:** the platform APIs for the wrapper's audio tool are PipeWire monitor sources, WASAPI loopback, and ScreenCaptureKit audio or Core Audio process taps. They come from general platform knowledge, not from this research. Output should be a WAV/FLAC file path plus optional MCP `audio` content. Harness forwarding of audio is covered in `harness_integration.md` §7.
