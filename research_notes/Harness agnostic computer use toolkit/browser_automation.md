# Browser automation for AI agents (state as of 2026-10-07): options, benchmarks, real-browser attach, desktop+browser coordination, Firefox

Method note: Repo stats (stars, license, last push, latest release) were pulled live from the public GitHub REST API and npm/PyPI registries on 2026-10-07; READMEs were read from the default branch on the same day. Secondary/vendor claims are labeled. Anything from background knowledge (pre mid-2026) that could not be re-verified is labeled "unverified".

## Q1. What are the leading agent browser-control options, and how do they compare (interface, engine, attach-to-real-browser, headless, snapshot format, token efficiency, license, maintenance, 2026 changes)?

### Takeaway
The field has consolidated around three open-source, harness-agnostic "browser tools for coding agents" that all use the same core pattern (accessibility-tree snapshot with short element refs, then act by ref): Microsoft Playwright (MCP + the newer `playwright-cli` + skills), Google's chrome-devtools-mcp (MCP + experimental CLI, Puppeteer/CDP), and Vercel's agent-browser (native Rust CLI + optional MCP, direct CDP). browser-use moved its coding-agent offering to a minimal raw-CDP "Browser Harness". Everything else is either an autonomous agent framework (browser-use library, Stagehand, Skyvern, Notte, nanobrowser), a cloud browser host (Browserbase, Steel, Kernel, Hyperbrowser, Anchor), or an alternative engine (Lightpanda).

**Playwright MCP (`@playwright/mcp`)**
- Interface: MCP server; engine: Playwright; "uses Playwright's accessibility tree, not pixel-based input... No vision models needed." — [playwright-mcp README](https://github.com/microsoft/playwright-mcp)
- The README itself now steers coding agents to the CLI: "Modern coding agents increasingly favor CLI–based workflows exposed as SKILLs over MCP because CLI invocations are more token-efficient: they avoid loading large tool schemas and verbose accessibility trees into the model context." MCP is positioned for "exploratory automation, self-healing tests, or long-running autonomous workflows." — [playwright-mcp README](https://github.com/microsoft/playwright-mcp)
- Browsers: `--browser` accepts chrome, firefox, webkit, msedge. Modes: persistent profile (default), `--isolated` (in-memory) with `--storage-state`, `--user-data-dir`, `--cdp-endpoint` (attach over CDP), and `--extension` ("Connect to a running browser instance (Edge/Chrome only). Requires the 'Playwright Extension'"). `--headless` (headed by default). — [playwright-mcp README](https://github.com/microsoft/playwright-mcp)
- Opt-in capability groups via `--caps`: vision (coordinate-based), pdf, devtools, network, storage, config, testing. `--snapshot-mode full|none`. `--secrets` (dotenv file; matching plaintext is replaced in tool responses so the LLM doesn't see it). `--allowed-origins` explicitly "*does not* serve as a security boundary." `--mobile` emulation noted as token-saving. Docker image is headless Chromium only. — [playwright-mcp README](https://github.com/microsoft/playwright-mcp)
- Playwright Chrome Extension (Chrome Web Store "Playwright Extension"): connects to tabs in the user's existing browser "and leverage the state of your default user profile"; user picks which tab on first connect; per-connection approval dialog unless `PLAYWRIGHT_MCP_EXTENSION_TOKEN` is set; multiple clients each get their own colored tab group and only see tabs in that group; `--profile-dir-name` selects a Chrome profile. — [Playwright extension README](https://github.com/microsoft/playwright/tree/main/packages/extension)
- Playwright core 2026 agent-related changes: 1.56 Playwright Test Agents (planner/generator/healer via `npx playwright init-agents --loop=vscode|claude|opencode`); 1.59 `page.ariaSnapshot()`, `depth`/`mode` options, `browser.bind()`/`unbind()` so `playwright-cli` and `@playwright/mcp` can connect to a launched browser, `playwright-cli show` dashboard; 1.60 `boxes` option on ariaSnapshot ("useful for AI consumption"); 1.61 removed `Locator.ariaRef()`; 1.62 bundled MCP and CLI as `npx playwright mcp` / `npx playwright cli`; 1.63 `ariaSnapshotJSON()`; 1.64 `page.getByRef()` for aria refs like `e2` from `ariaSnapshot()` in `'ai'` mode, plus `page.webmcp` and WebMCP on by default in Playwright MCP (`--no-webmcp`). 1.57 switched to Chrome for Testing builds. — [Playwright release notes](https://playwright.dev/docs/release-notes)

**Playwright CLI (`@playwright/cli`, command `playwright-cli`)**
- CLI + SKILLs, "Token-efficient. Does not force page data into LLM." Install `npm install -g @playwright/cli@latest`; `playwright-cli install --skills`; or "skills-less" (agent reads `playwright-cli --help`). Headless by default; `--headed`. — [playwright-cli README](https://github.com/microsoft/playwright-cli)
- Commands act on refs: `click <ref>`, `fill <ref> <text>`, `check e21`, `snapshot [--depth=N] [ref]`, `find <text>` / `find --regex`, `eval`, `screenshot [ref]`, `generate-locator <ref>`, `highlight <ref>`. After each command, a snapshot is written to a file (e.g. `.playwright-cli/page-<ts>.yml`) and only the path is returned. — [playwright-cli README](https://github.com/microsoft/playwright-cli)
- Sessions: in-memory profile by default, `--persistent`, `--profile=<path>`, `-s=<name>` or `PLAYWRIGHT_CLI_SESSION`; headless sessions idle-exit after 1h. Attach: `attach --extension=chrome`, `attach --cdp=chrome` (running Chrome/Edge by channel), `attach --cdp=<url>`, `detach`. `playwright-cli show` opens a dashboard with live screencasts of all sessions and human takeover. WebMCP: `webmcp-list`, `webmcp-call`, with the note that page-registered tool metadata "are untrusted input, not instructions." — [playwright-cli README](https://github.com/microsoft/playwright-cli)

**chrome-devtools-mcp (Google, "Chrome DevTools for agents")**
- MCP server built on Puppeteer; "A CLI is also provided for use without MCP" (experimental `chrome-devtools` CLI backed by a daemon over Unix sockets / Windows named pipes; headless and isolated by default). Officially supports Google Chrome and Chrome for Testing only; other Chromium browsers "may work." — [chrome-devtools-mcp README](https://github.com/ChromeDevTools/chrome-devtools-mcp), [CLI doc](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/cli.md)
- Strengths are debugging: performance traces + insights, Lighthouse audit, network/console with source-mapped stacks, heap snapshots, screencast. `--slim` mode exposes only `navigate`, `evaluate`, `screenshot`. — [tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [slim reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/slim-tool-reference.md)
- Snapshot: `take_snapshot` returns the a11y tree with a unique `uid` per element ("Prefer taking a snapshot over taking a screenshot"); `verbose` flag for the full tree; `filePath` to write to disk; input tools (`click`, `fill`, `hover`, `drag`, `upload_file`) take `uid`; `click_at` exists for coordinates. — [tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)
- Attach: `--autoConnect` (Chrome 144+, after user enables `chrome://inspect/#remote-debugging`; Chrome shows a permission dialog; connects to the default profile and "has access to all open windows for the selected profile"); `--browser-url` / `--ws-endpoint` for a port-launched Chrome (requires non-default `--user-data-dir`). — [advanced usage](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md), [configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)
- Privacy defaults to note: Google usage statistics collection is "enabled by default" (opt out `--no-usage-statistics`; auto-disabled if `CI` set); performance tools may send URLs to CrUX (`--no-performance-crux`); npm update checks. — [chrome-devtools-mcp README](https://github.com/ChromeDevTools/chrome-devtools-mcp)
- Design principles published: agent-agnostic (MCP), token-optimized semantic summaries, "Files are the right location for large amounts of data", small deterministic tools, self-healing errors, "Reference over Value" (return file paths for screenshots/traces). Recommended as the base for "an integrated browser subagent" (reference: Gemini CLI browser agent). — [design principles](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/design-principles.md), [README](https://github.com/ChromeDevTools/chrome-devtools-mcp)

**vercel-labs/agent-browser**
- "Browser automation CLI for AI agents. Fast native Rust CLI." Client-daemon; daemon is "Pure Rust... using direct CDP, no Node.js required." Native binaries for macOS ARM64/x64, Linux ARM64/x64, **Windows x64**. Engines: `--engine chrome|lightpanda|obscura`, plus Safari via WebDriver for iOS. `agent-browser install` fetches Chrome for Testing; existing Chrome/Brave/Playwright/Puppeteer installs auto-detected. — [agent-browser README](https://github.com/vercel-labs/agent-browser)
- Snapshot: `snapshot` → `- button "Submit" [ref=e2]`; act with `click @e2`. Filters `-i` (interactive only), `-c` (compact), `-d N`, `-s <css>`, `-u` (hrefs), `--delta` (full once, then `unchanged` or structural JSON delta). "Surviving DOM elements keep their refs across snapshots." `screenshot --annotate` overlays numbered labels where `[N]` == `@eN` (set-of-marks bridging visual and text refs). Clicks "fail early when another element covers the target's click point." Batch execution and command chaining. — [agent-browser README](https://github.com/vercel-labs/agent-browser)
- MCP: `agent-browser mcp [--tools core|network|react|all]`; default `core` profile "keeps MCP context small." Skills: `agent-browser skills get <name>` serves skill content matched to the installed CLI version. — [agent-browser README](https://github.com/vercel-labs/agent-browser)
- Auth/real browser: `--profile <name>` reuses a Chrome profile by copying it to a temp dir ("read-only snapshot"; on Windows close Chrome first); `--auto-connect` discovers running Chrome via `DevToolsActivePort`, ports 9222/9229, then direct WebSocket (explicitly for "Chrome 144+ ... chrome://inspect/#remote-debugging (which uses a dynamic port)"); `state save/--state`, `--session --restore`, encrypted auth vault (`auth save/login`, LLM never sees passwords). — [agent-browser README](https://github.com/vercel-labs/agent-browser)
- Security features (opt-in): `--content-boundaries` (delimit untrusted page output), `--allowed-domains` (blocks subresources, WebSockets, beacons, disables WebRTC; refused for auto-connect/profile modes because containment can't be installed first), `--action-policy`, `--confirm-actions eval,download`, `--max-output`. Also an observability dashboard, streaming, iOS simulator, provider integrations (Browserless, Browserbase, Browser Use, Kernel, AgentCore). — [agent-browser README](https://github.com/vercel-labs/agent-browser)

**SawyerHood/dev-browser**
- Agent writes short JavaScript run against a warm daemon; v1.0 (rc) "replaces the Playwright/QuickJS implementation from dev-browser 0.2 with the Puppeteer/Bun implementation"; `page.snapshot({interactive:true})` returns a11y tree with refs like `e12`, usable as `page.click("ref/e12")`; `page.shot()` returns JPEG path + CSS-pixel dimensions. MCP tools `dev_browser_run`, `dev_browser_pages`, etc. `dev-browser install-skill --codex|--claude|--agents`. Platforms: "macOS and glibc Linux are supported; Windows and musl Linux are not yet supported." `dev-browser chrome` launches a dedicated profile because "Chrome 136 and newer ignore remote-debugging flags on the default profile"; `--connect` takes auto-discovery, port, URL, ws URL or CDP Unix socket. Benchmarks (warm daemon): snapshot ~18 ms, screenshot ~36 ms, cold start ~280 ms. Notes `node:vm` "is not a security sandbox." — [dev-browser README](https://github.com/SawyerHood/dev-browser)

**browser-use (library, CLI, Browser Harness, cloud)**
- Three paths: hosted cloud agent API; CLI for coding agents ("Claude Code, Codex, Hermes, OpenClaw, Pi, Cursor"); Python library (`uv add browser-use`) with own agent loop and BU2 model (`ChatBrowserUse(model='bu-2-0')`). README advertises cloud browser at "$0.02 per browser-hour" with stealth/CAPTCHA/proxies. Ships "Browser Use toolsets for Claude": implements all 31 actions of Anthropic's browser toolset against local, cloud or existing CDP browser. — [browser-use README](https://github.com/browser-use/browser-use)
- The CLI (`uv tool install browser-use`) "is built on Browser Harness"; agents run Python; by default it attaches to the user's running Chrome/Chromium over CDP (user may need to approve Chrome's remote-debugging prompt); `BU_CDP_URL`/`BU_CDP_WS` for other CDP browsers; `browser-use --doctor`. — [Browser Use CLI docs](https://docs.browser-use.com/open-source/browser-use-cli.md)
- Browser Harness: "Connect an LLM directly to your real browser through one editable CDP websocket. The agent writes missing helpers as it works"; setup has the agent open `chrome://inspect/#remote-debugging` and the user tick the checkbox; `browser-harness-mcp` exposes helpers as MCP tools. — [browser-harness README](https://github.com/browser-use/browser-harness)
- Rationale (Apr 19, 2026): ~600 lines total (`run.py`, `helpers.py` 192 lines of thin CDP wrappers the agent can edit, `daemon.py`, `SKILL.md`); claims "LLMs already know CDP," raw CDP handles cross-origin iframes/Shadow DOM, and they removed "thousands of lines of element extractors, DOM indexers, and click wrappers"; no formal benchmark given. — [Browser Use blog: Bitter Lesson of Agent Harnesses](https://browser-use.com/posts/bitter-lesson-agent-harnesses)

**Browserbase Stagehand (v3 → v4) and Director**
- Stagehand is now "the SDK for browser agents" in TypeScript, Python and Go; primitives `act`, `observe` (returns real selectors so "credentials never reach the model"), `extract` (schema-validated); `localBrowser.launch({userDataDir})` or `browserbase.launch()`; claims "Hybrid accessibility-tree trimming," WebMCP, deep locators for iframes/closed Shadow DOM, OTel; Browserbase Model Gateway and server-side action caching. — [stagehand README](https://github.com/browserbase/stagehand)
- v4 docs: drives Chromium over CDP "and has no Playwright or Puppeteer dependency"; "runs next to the page"; `metrics()` reports per-method token usage. — [Stagehand v4 docs](https://docs.stagehand.dev/v4/first-steps/introduction)
- Browserbase's MCP is now hosted (`navigate`, `act`, `observe`, `extract`, "no install, no local browser"); the old open-source `mcp-server-browserbase` repo is archived. — [stagehand README](https://github.com/browserbase/stagehand); archive status from [GitHub API](https://github.com/browserbase/mcp-server-browserbase)

**Cloud browser hosts (Steel, Kernel, Hyperbrowser, Anchor)**

- Kernel: sandboxed headful Chromium in Docker or Unikraft unikernels; CDP on 9222; unikernel standby snapshots preserve auth/state. — [kernel-images README](https://github.com/kernel/kernel-images)

Source is Notte (a competitor) — treat as biased. — [Notte comparison](https://ai.notte.cc/answers/anchor-browser-vs-hyperbrowser), [Anchor MCP docs](https://docs.anchorbrowser.io/advanced/mcp-open-source.md)

**Agent frameworks (Skyvern, Notte, LaVague, nanobrowser)**
- Skyvern: "Automate Browser-based workflows using LLMs and Computer Vision"; Playwright-compatible SDK + no-code workflow builder; AGPL-3.0; technical report claims 85.8% WebVoyager (Skyvern 2.0). — [Skyvern README](https://github.com/Skyvern-AI/skyvern)

**Lightpanda (headless engine for agents)**
- "Not a Chromium fork... written in Zig" with V8; claims 123 MB vs 2 GB peak memory and 5 s vs 46 s for 100 pages vs headless Chrome (vendor benchmark); CDP server and WebDriver BiDi (`--protocol webdriver --protocol cdp`); `--dump markdown`; native MCP (`lightpanda mcp`, stdio or HTTP with `Mcp-Session-Id` sessions); `lightpanda agent` emits replayable "PandaScript"; no native Windows binary (WSL only); telemetry on by default (`LIGHTPANDA_DISABLE_TELEMETRY=true`). Hit 1.0.0 on 2026-10-02. — [Lightpanda README](https://github.com/lightpanda-io/browser); release date from [GitHub API](https://github.com/lightpanda-io/browser/releases)
- agent-browser can use Lightpanda as an engine (`--engine lightpanda`). — [agent-browser README](https://github.com/vercel-labs/agent-browser)

**Reference designs (first-party products)**
- Anthropic `browser_toolset_20260801` (Claude API, GA, client-executed): 27 default member tools + 4 opt-in (`javascript_exec`, `file_upload`, `read_console`, `read_network`) = 31. Observation via `read_page` (a11y tree, `filter` visible/`interactive`/`all`, `depth` default 15, capped 50,000 chars), `find` (natural-language, ≤20 matches), `get_page_text`, `screenshot`, `zoom`. Refs formatted like `button "Search" [ref_4]`; targets are `{type:"ref"}` or `{type:"coordinate"}` in **viewport pixels**; refs scoped to a tab, valid until navigation/material DOM change; executor must return explicit stale-ref errors and never renumber. Docs: "A tree read often costs fewer input tokens and gives Claude actionable references." GA status conflicts: Claude Code docs say beta; Gigazine reports GA announced Aug 26, 2026. — [Claude Code Chrome docs](https://code.claude.com/docs/en/chrome), [Claude help center](https://support.claude.com/en/articles/12012173-get-started-with-claude-in-chrome); contradicted/updated by [Gigazine 2026-08-27](https://gigazine.net/gsc_news/en/20260827-claude-chrome-available/)

- Chrome "auto browse" (Gemini 3, launched late Jan 2026, US AI Pro/Ultra): agent tab badged with cursor+sparkle, glow outline, side-panel step list; Password Manager use requires explicit authorization. — [9to5Google 2026-01-28](https://9to5google.com/2026/01/28/chrome-gemini-auto-browse/), [eesel.ai](https://eesel.ai/blog/chrome-auto-browse-how-to-use-geminis-new-ai-agent-feature)

### Inferences
- The ref-based a11y snapshot (`[ref=eN]` / `uid` / `ref_N`) is now the de facto standard across Playwright, chrome-devtools-mcp, agent-browser, dev-browser and Anthropic's own browser toolset; a toolkit should adopt it rather than invent a new format.
- For a cross-platform toolkit that must run on Windows, agent-browser (native Rust, Windows x64) and Playwright (Node, Win/mac/Linux) are the safest dependencies; dev-browser (no Windows) and Lightpanda (no native Windows) are not.
- chrome-devtools-mcp is best-in-class for debugging/perf but is Chrome-only and has telemetry on by default; better as an optional companion than as the core driver.
- Stagehand, browser-use library, Skyvern, Notte and nanobrowser embed their own LLM loop (an agent inside the agent). For a toolkit whose "brain" is the host harness (Claude Code/Codex/opencode/pi), these are the wrong layer; the right layer is deterministic primitives.
- Playwright MCP still versioned 0.0.x after 18 months, but ships weekly and is now bundled into Playwright core (1.62), so it's effectively stable infrastructure.

## Q2. What do benchmarks and token-cost comparisons show about which approaches work best (WebVoyager, Online-Mind2Web, BrowseComp, WebArena; a11y snapshot vs screenshot)?

### Takeaway
Public leaderboards are saturated on WebVoyager (~99%) and near-saturated on Online-Mind2Web (90–97%) but mostly measure model+agent systems, use incompatible judges, and say little about which tool interface is better. The only controlled tool-interface comparison found (Ranger, Apr 2026) shows CLI/file-based snapshots cut context 2–3x but needed ~3x more tool calls, ran 2–3x slower, and did not reduce cost; a11y snapshots are consistently reported as roughly 6–50x cheaper than screenshots per observation (mostly vendor/anecdotal numbers).

### Cited Findings
- Steel leaderboard (last updated Sep 30, 2026): WebVoyager top entries browser-control (Fable 5) 99.19%, Alumnium 98.5%, Surfer 2 97.1%; Online-Mind2Web: Browser Use Cloud (bu-max) 97.0%, GPT-5.4 Native Computer Use 93.0%, ABP + Claude Opus 4.6 90.53%; BrowseComp: GPT-5.6 Sol Ultra 92.2%; WebArena: WebTactix (DeepSeek v3.2) 74.3%. ## Q3. How can an agent safely use the user's real, logged-in browser (Chrome 136+ restrictions, extension bridges, separate profiles, cookie import), and what are the security concerns?

### Takeaway
Since Chrome 136, `--remote-debugging-port/pipe` is ignored on the default user-data-dir, so there are now four routes: (1) Chrome 144+ `chrome://inspect/#remote-debugging` toggle with a per-connection consent dialog (sanctioned path to the real profile, uses a dynamic port discoverable via `DevToolsActivePort`); (2) an extension bridge (Playwright Extension, Claude in Chrome, Codex Chrome extension) with tab-scoped access; (3) a dedicated agent profile launched with a debug port; (4) copying/importing state (profile copy, storage-state JSON). Prompt injection via page content remains unsolved; vendors rely on classifiers, confirmations, allowlists and isolation.

### Cited Findings
- Chrome 136 change (blog Mar 17, 2025): `--remote-debugging-port` and `--remote-debugging-pipe` "will no longer be respected if attempting to debug the default Chrome data directory"; must use a non-standard `--user-data-dir`, which "uses a different encryption key"; motivated by infostealers using remote debugging to extract cookies after App-Bound Encryption; recommends Chrome for Testing for automation (keeps old behavior). — [Chrome for Developers blog](https://developer.chrome.com/blog/remote-debugging-port)
- Chrome 144+: enable via `chrome://inspect/#remote-debugging`, "Follow the dialog UI to allow or disallow incoming debugging connections"; chrome-devtools-mcp `--autoConnect` then connects to the default profile and has access to all its windows; Chrome shows a permission dialog. — [chrome-devtools-mcp advanced usage](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)
- Toggle-enabled browsers publish a WebSocket endpoint in `DevToolsActivePort` but `/json/version` returns 404; verified on Chrome 151 that the port flag does not open on the default profile; cua treats the toggle as "the only route for a real user profile" (issue opened Aug 5, 2026). — [trycua/cua#2916](https://github.com/trycua/cua/issues/2916)
- agent-browser `--auto-connect` reads `DevToolsActivePort`, then probes 9222/9229, then direct WebSocket, explicitly to support the Chrome 144+ dynamic-port toggle. — [agent-browser README](https://github.com/vercel-labs/agent-browser)
- browser-use Browser Harness / CLI attach to the user's running Chrome by default after the user ticks the checkbox at `chrome://inspect/#remote-debugging`. — [browser-harness README](https://github.com/browser-use/browser-harness), [Browser Use CLI docs](https://docs.browser-use.com/open-source/browser-use-cli.md)
- Extension bridges: Playwright Extension (tab picker, per-connection approval or token, per-client tab groups, Chrome/Edge only) — [Playwright extension README](https://github.com/microsoft/playwright/tree/main/packages/extension); Claude in Chrome (native messaging host; Chrome/Edge only; pauses on login/CAPTCHA; "enhanced with our safety classifiers but is still risky") — [Claude Code Chrome docs](https://code.claude.com/docs/en/chrome), [Claude help center](https://support.claude.com/en/articles/12012173-get-started-with-claude-in-chrome)
- Dedicated profiles: dev-browser `dev-browser chrome --profile work` uses a dedicated profile; pi-computer-use `launch_browser` creates a temporary CDP profile bound to a random loopback port; Cua's recommended route launches a driver-owned isolated profile deleted at session end, and attaching an existing signed-in profile needs explicit authorization; "Cua Driver therefore never enables remote debugging as a side effect of inspection." — [dev-browser README](https://github.com/SawyerHood/dev-browser), [pi-computer-use config](https://cdn.jsdelivr.net/npm/@injaneity/pi-computer-use@0.5.1/docs/configuration.md), [Cua blog](https://cua.ai/blog/extension-free-browser-use)
- Cookie/state import: agent-browser `--profile Default` copies the Chrome profile to a temp dir (read-only snapshot; Windows requires Chrome closed); `--auto-connect state save ./auth.json` then `--state`; state files are plaintext tokens unless `AGENT_BROWSER_ENCRYPTION_KEY` set; warns "`--remote-debugging-port` exposes full browser control on localhost. Any local process can connect." Playwright MCP `--storage-state`; Stagehand `userDataDir`. — [agent-browser README](https://github.com/vercel-labs/agent-browser), [playwright-mcp README](https://github.com/microsoft/playwright-mcp), [stagehand README](https://github.com/browserbase/stagehand)
- chrome-devtools-mcp notes some sites block sign-in when the browser is controlled via WebDriver-style launch, one reason to attach to a user-started Chrome. — [advanced usage](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md)
- Anthropic's recommended precautions for browser agents: dedicated VM/container, fresh profile without credentials, network-layer host allowlist re-checked after redirects, block loopback/link-local/private ranges, only http/https schemes, keep `javascript_exec`/`file_upload` off, human confirmation for consequential actions; server-side prompt-injection classifiers scan page content. — [Claude browser use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)
- Prompt injection track record (mostly secondary sources): Brave found Comet acting on hidden text/screenshot instructions (2025); Atlas injected within 24h of launch (Oct 2025); Trail of Bits audit for Perplexity (Feb 2026) found four data-exfiltration methods from logged-in sessions; UW study: 4 of 7 agentic browsers could bypass same-origin policy; OpenAI introduced "Lockdown Mode" (Feb 2026) and said injection "may never be fully patched"; Aug 2026 analysis says Atlas/Comet/Dia/Copilot still vulnerable. — [Brave/Shivan Kaul](https://shivankaul.com/blog/prompt-injections-in-agentic-browsers), [Varonis](https://www.varonis.com/blog/architectural-vulnerabilities-in-agentic-llm-browsers), [SecurityArsenal](https://securityarsenal.com/blog/ai-browser-prompt-injection-why-openai-atlas-perplexity-comet-and-copilot-still-leak-and-how-to-defend-your-enterprise), [SoftwareSeni](https://www.softwareseni.com/six-demonstrated-exploits-that-prove-agentic-browser-security-is-not-theoretical/)
- Mitigation patterns in tools: agent-browser `--content-boundaries`, domain allowlist, action policy, confirm-actions, auth vault where "The LLM never sees passwords"; Playwright MCP `--secrets` redaction; Stagehand `observe()` → fill locally so "credentials never reach the model"; Playwright CLI/WebMCP output labeled untrusted. — [agent-browser README](https://github.com/vercel-labs/agent-browser), [playwright-mcp README](https://github.com/microsoft/playwright-mcp), [stagehand README](https://github.com/browserbase/stagehand), [playwright-cli README](https://github.com/microsoft/playwright-cli)
- Mozilla warns: never run firefox-devtools-mcp against your regular profile; Marionette sets `navigator.webdriver = true` and can trip bot defenses. — [Firefox source docs](https://firefox-source-docs.mozilla.org/ai-agent-tools/firefox-devtools-mcp.html)

### Inferences
- Recommended toolkit policy: default to a dedicated, persistent agent profile (headed or headless) the user logs into once; offer "attach to my real Chrome" only via the Chrome 144+ toggle (with discovery through `DevToolsActivePort`, not `/json/version`) or an extension bridge, and require explicit opt-in per session.
- Copying the real profile to a temp dir may silently lose encrypted cookies on some OSes, since Chrome says non-default data dirs use a different encryption key (unverified inference; agent-browser offers the feature anyway, and Windows App-Bound Encryption makes this most likely there).
- Wrap all page-derived text in boundary markers and treat WebMCP tool descriptions as untrusted; gate eval/download/upload/navigation-to-new-origin behind confirmation when attached to a real profile.

### Gaps
- No primary Chrome blog post found for the Chrome 144 `chrome://inspect/#remote-debugging` toggle itself (documented only via chrome-devtools-mcp docs and third-party tools); exact consent UX and whether it is per-connection or per-session not confirmed.
- Whether Debian's Chromium package (vs Google Chrome) exposes the same toggle and `DevToolsActivePort` behavior was not verified.
- Primary Trail of Bits / UW / OpenAI Lockdown Mode documents were not opened; figures are from secondary aggregators.

## Q4. How should a desktop computer-use toolkit coordinate with a browser tool (detect focused browser and switch to DOM mode, share coordinates, or just recommend Playwright MCP / chrome-devtools-mcp)? Are there projects already combining desktop + browser control well?

### Takeaway
Several 2026 projects already merge desktop and browser control: Cua Driver binds a CDP tab to a verified OS window/process (macOS/Windows/Linux, Aug 2026), pi-computer-use (a pi extension) folds CDP pages into the same state model as desktop UI, dcc-cua uses a CDP → DOM → window-a11y → pixels fallback chain, and Anthropic's API lets the browser and computer-use toolsets be declared together with separate coordinate frames. The common pattern is: route web work through CDP refs, keep pixels as fallback, and keep the two coordinate frames separate rather than unifying them.

### Cited Findings
- Cua Driver (published Aug 6, 2026; stable in v0.19.0): starting from a PID and window ID, verifies the loopback DevTools endpoint belongs to that process, then links the OS window to the browser target and returns session-scoped opaque capabilities — proof that "one operating-system window and one browser tab were the same surface"; `get_browser_state` with `semantic_v2` returns a semantic outline with short-lived action refs invalidated by navigation/reconnect/newer snapshot; "Proven routes act. Ambiguous or unsupported routes return structured refusals"; "puts the bridge below the agent, inside an agent-neutral computer-use driver"; platforms macOS, Windows, "validated Linux configurations." Coordinate mapping between page and screen not described; on-screen cursor overlay is visual only. — [Cua blog](https://cua.ai/blog/extension-free-browser-use)
- Background tabs remain addressable while Chrome is unfocused under Cua's anchoring. — [runtimewire](https://runtimewire.com/article/cua-extension-free-chromium-control-agent-driver)
- dcc-cua fallback chain: "CUA's typed CDP routes first, then a browser semantic/DOM adapter, exact-window OS accessibility, and finally explicitly approved exact-window pixels"; per-app profiles with window/URL selectors, preferred route, dialog policy. — [dcc-cua](https://gitblind.noratr.app/dcc-mcp/dcc-cua)
- pi-computer-use (pi extension): `PI_COMPUTER_USE_CDP_PORT` enables CDP; discovered browser pages "join the same root and state system as desktop UI"; `launch_browser` makes a temp CDP profile on a random loopback port; `navigate_browser`/`evaluate_browser` only for CDP page states while native browser windows still use desktop observe/act; config precedence `.pi/computer-use.json` > `~/.pi/agent/extensions/pi-computer-use.json`, env overrides. — [pi-computer-use configuration](https://cdn.jsdelivr.net/npm/@injaneity/pi-computer-use@0.5.1/docs/configuration.md)
- Anthropic: browser toolset uses viewport pixels with origin at page top-left ("There is no desktop or window frame"); computer use uses desktop screenshot pixels; "Can be declared together; calls are distinguished by `toolset_name`"; guidance: browser use for tasks inside webpages, computer use when a full desktop is needed. — [Claude browser use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)
- OpenAI Codex (third-party summary): three tiers — Computer Use (pixel, foreground-only on Windows), Browser Use (DOM-aware in-app browser or connected Chrome), and Chrome DevTools MCP for CLI/headless. — [Daniel Vaughan blog](https://codex.danielvaughan.com/2026/06/12/codex-browser-use-developer-mode-cdp-dom-snapshots-2x-performance-cli-frontend-workflows/)
- Asteroid: vision desktop control costs more time/money; steer to browser use whenever sufficient; "DOM-first execution with a vision backup" is the current sweet spot. — [Asteroid node capabilities](https://docs.asteroid.ai/concepts/node-capabilities), [Asteroid blog](https://asteroid.ai/blog/when-will-browser-agents-do-real-work)
- Playwright 1.60 added a `boxes` option to `ariaSnapshot()` (bounding boxes in snapshots), and agent-browser's annotated screenshots map visual labels to refs — both are ways to tie refs to pixels. — [Playwright release notes](https://playwright.dev/docs/release-notes), [agent-browser README](https://github.com/vercel-labs/agent-browser)
- Playwright CLI and agent-browser both offer live dashboards (screencast + human takeover), useful for a human watching a headless agent browser. — [playwright-cli README](https://github.com/microsoft/playwright-cli), [agent-browser README](https://github.com/vercel-labs/agent-browser)
- Cua issue cross-references a separate "accessibility flag needed on Linux" issue (#2915) for browser/desktop integration. — [trycua/cua#2916](https://github.com/trycua/cua/issues/2916)

### Inferences
- Practical design for this toolkit: (a) expose a separate `browser_*` tool family (or CLI subcommand) using CDP refs in viewport coordinates; (b) in desktop observe, when the focused window is a Chromium browser that the toolkit controls (or is attached to via CDP), annotate the observation with "browser tab X is controllable — prefer browser tools"; (c) only convert coordinates when needed using window bounds + CDP `Browser.getWindowForTarget`/`Page.getLayoutMetrics` (my suggestion, not seen documented in these projects); (d) keep pixels as an explicit fallback for canvas, native dialogs (file pickers, permission prompts, extension popups), and non-controllable browsers (e.g., stock Firefox).
- Detect-and-switch only works if the browser was launched/attached with CDP; for an arbitrary user Chrome without the toggle, the toolkit cannot silently switch modes (and Cua deliberately refuses to enable debugging as a side effect).
- "Just recommend installing Playwright MCP/chrome-devtools-mcp alongside" is the lowest-effort option but leaves the agent with two unrelated coordinate systems and two Chrome instances (the MCP's own launched browser vs the one on screen) — confusing for a desktop agent. A thin integrated layer that controls the same on-screen browser avoids that.

### Gaps
- No project found that documents a formal page↔screen coordinate transform (DPI, browser chrome offsets, zoom) for mixing CDP and OS input; Cua's post explicitly doesn't cover it.
- pi-computer-use platform matrix and maturity not confirmed; dcc-cua seen only via a mirror.
- No evidence that unified desktop+browser control improves benchmark success (Cua's OSWorld 2.0 gain was not significant).

## Q6. Recommendation: should the toolkit embed/wrap one, depend on one, or build a thin layer — and which design patterns are worth copying?

### Takeaway
Build a thin, CDP-direct browser layer inside the toolkit (same process/daemon as desktop control) that copies the converged ref-snapshot design, and document/optionally delegate to agent-browser or Playwright for power features; do not embed an LLM-driven agent framework. Evidence: every leading tool converged on the same small primitive set; the user-real-browser path (Chrome 144 toggle + `DevToolsActivePort`) is simple CDP; agent-browser proves a native single-binary CDP daemon works cross-platform; browser-use's ~600-line harness shows thin is viable; and integrating with the desktop layer (same on-screen browser, window binding) is something none of the standalone browser tools do.

### Cited Findings
- Converged primitives across tools: snapshot with refs (`[ref=e2]` Playwright/agent-browser; `uid` chrome-devtools-mcp; `ref/e12` dev-browser; `[ref_N]` Anthropic), act-by-ref (click/fill/hover/select/drag/upload), navigate/tabs, screenshot (optionally annotated), eval, wait. — [playwright-cli README](https://github.com/microsoft/playwright-cli), [chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [agent-browser README](https://github.com/vercel-labs/agent-browser), [dev-browser README](https://github.com/SawyerHood/dev-browser), [Claude browser use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)
- Daemon + thin client pattern for CLI tools (state persists across invocations): agent-browser (Rust daemon, 1h idle exit, never auto-closes headed/user-attached browsers), chrome-devtools CLI (daemon over Unix socket/named pipe), dev-browser (warm daemon ~13 ms/script), playwright-cli sessions (`-s=`), browser-harness `daemon.py`. — [agent-browser README](https://github.com/vercel-labs/agent-browser), [chrome-devtools CLI](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/cli.md), [dev-browser README](https://github.com/SawyerHood/dev-browser), [playwright-cli README](https://github.com/microsoft/playwright-cli), [Bitter Lesson post](https://browser-use.com/posts/bitter-lesson-agent-harnesses)
- Dual interface (CLI+skill and MCP from the same core): Playwright (MCP + CLI, both bundled in core since 1.62), agent-browser (`agent-browser mcp`), dev-browser (`dev-browser mcp`), chrome-devtools-mcp (MCP + CLI), browser-harness (`browser-harness-mcp`). Skills installed per-harness: dev-browser `install-skill --codex|--claude|--agents` to `~/.codex/skills`, `~/.claude/skills`, `~/.agents/skills`; agent-browser serves version-matched skills from the binary; `playwright-cli install --skills`. — same sources as above, [Playwright release notes](https://playwright.dev/docs/release-notes)
- Token-control patterns: tool-profile gating (`--tools core` default; Playwright `--caps`; chrome-devtools `--slim`), interactive-only/compact/depth/selector-scoped snapshots, `--delta` snapshots, `find <text>` over snapshot, file-path returns for heavy artifacts ("Reference over Value"), `--max-output`, `--mobile` lighter pages. — [agent-browser README](https://github.com/vercel-labs/agent-browser), [playwright-mcp README](https://github.com/microsoft/playwright-mcp), [playwright-cli README](https://github.com/microsoft/playwright-cli), [design principles](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/design-principles.md)
- Ref lifecycle rules: refs stable for surviving DOM elements across snapshots (agent-browser); refs scoped to tab, valid until navigation/material DOM change, never renumbered, explicit stale-ref error text (Anthropic); session-scoped refs invalidated by navigation/reconnect/newer snapshot (Cua). — [agent-browser README](https://github.com/vercel-labs/agent-browser), [Claude browser use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool), [Cua blog](https://cua.ai/blog/extension-free-browser-use)
- Actionable errors: agent-browser reports the covering element when a click target is obscured; chrome-devtools-mcp "Self-Healing Errors: Return actionable errors that include context and potential fixes." — [agent-browser README](https://github.com/vercel-labs/agent-browser), [design principles](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/design-principles.md)
- Escape hatch: code execution against the page (Playwright `eval`, chrome-devtools `evaluate_script`, dev-browser JS scripts, browser-harness Python over raw CDP) — browser-use argues raw CDP + agent-written helpers outperforms thick wrappers (no benchmark). — [Bitter Lesson post](https://browser-use.com/posts/bitter-lesson-agent-harnesses), [dev-browser README](https://github.com/SawyerHood/dev-browser)
- Interface-design tradeoff: returning page state with each action (MCP style) minimizes round trips and wall-clock; file-only snapshots minimize context but add calls. — [Ranger](https://outpost.ranger.net/post/the-hidden-cost-of-fewer-tokens/)
- WebMCP is now supported by Playwright (1.64, on by default in MCP), agent-browser, and Stagehand — pages can register agent tools. — [Playwright release notes](https://playwright.dev/docs/release-notes), [agent-browser README](https://github.com/vercel-labs/agent-browser), [stagehand README](https://github.com/browserbase/stagehand)
- Licensing: Playwright, chrome-devtools-mcp, agent-browser are Apache-2.0; dev-browser, browser-use, browser-harness, Stagehand MIT; Lightpanda and Skyvern AGPL-3.0; Notte SSPL — the latter three are problematic to embed in a permissively licensed toolkit. — GitHub API (see Q1 table), [Notte README](https://github.com/nottelabs/notte)

### Inferences
- Recommended architecture: one toolkit daemon that owns both desktop control and a CDP connection manager (launch dedicated profile / attach via toggle+`DevToolsActivePort` / attach via explicit ws URL / cloud ws URL). Expose `browser snapshot|click|fill|...` with refs as CLI subcommands + skill, and the same as MCP tools behind a `--tools`-style profile. Snapshot output: Playwright-style YAML-ish lines `- role "name" [ref=eN]` with interactive-only and delta modes; return a compact snapshot inline after mutating actions (cap size; spill to file with path when over budget).
- Implementation options, in order of preference: (1) thin own CDP layer (Rust/Go/Node) using `Accessibility.getFullAXTree` + `DOM.resolveNode`/backendNodeId mapping for refs (technique is background knowledge; matches what agent-browser/Stagehand v4 do natively); (2) depend on Playwright as a library (Node) — mature, cross-browser incl. patched Firefox, `ariaSnapshot({mode:'ai'})` + `getByRef()` now give refs natively (1.64), `connectOverCDP` for attach; (3) shell out to agent-browser as an optional backend for users who want its auth vault/allowlist/iOS features.
- Do not embed browser-use library, Stagehand, Skyvern, Notte or nanobrowser — they add an inner LLM loop, API keys and (for some) restrictive licenses; mention them only as alternatives for "hand off a whole web task" use cases.
- Ship docs/skills that tell agents: prefer browser tools over desktop clicks whenever the target is a controllable browser tab; fall back to screenshots/desktop for canvas, OS dialogs, and Firefox.

### Gaps
- No head-to-head reliability data for a thin custom CDP layer vs Playwright-based snapshots (iframes, shadow DOM, OOPIFs) — needs internal testing.
- Didn't verify Playwright's `'ai'` aria snapshot output format details beyond release-note mentions (background knowledge: `- button "Submit" [ref=e2] [cursor=pointer]`, unverified for 1.64).
