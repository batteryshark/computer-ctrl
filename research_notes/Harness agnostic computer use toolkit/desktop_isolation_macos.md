# macOS: a separate login session is the promising non-VM option

Researched 2026-10-13. Documentation research only; no accounts, sharing settings, sessions, permissions, or implementation changed. None of these configurations has been acceptance-tested with `cctl`.

## What Apple documents

**macOS supports a remotely controlled desktop belonging to a different logged-in user while the local person keeps working.** Apple Remote Desktop's “Connect to a virtual display” option shows the desktop of the account used to authenticate. When a different user owns the physical display, that user can continue uninterrupted. If the authenticated account already owns the physical display, or no one is logged in, the connection instead shows the physical session. Thus the account/session distinction is essential; “remote” alone does not imply isolation. [Apple: Choose how to control and observe](https://support.apple.com/guide/remote-desktop/choose-how-to-control-and-observe-apd4f46319e/mac)

This capability is not solely an Apple Remote Desktop product concept: Apple's **Ventura 13 Screen Sharing guide** explicitly describes concurrent login with a different username and screen through the “Log In” choice, instead of sharing the other remote user's display. That is version-specific documentation; the latest Screen Sharing page no longer explains this choice. Validate its current UI and behavior on the target macOS release before promising a built-in workflow. [Apple: Screen Sharing, Ventura](https://support.apple.com/guide/mac-help/share-the-screen-of-another-mac-mh14066/13.0/mac/13.0), [current guide](https://support.apple.com/guide/mac-help/share-the-screen-of-another-mac-mh14066/mac)

**Fast User Switching alone is not an active remote desktop.** Apple's archived developer guidance says switched-out processes continue running, but stop receiving physical keyboard/mouse input and see the monitor as asleep. Current AppKit documents notifications allowing applications to suspend work when their user session becomes inactive. A separately logged-in account is therefore insufficient evidence that screenshots, rendering, input injection, or animation keep working. [Apple: Supporting Fast User Switching](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPMultipleUsers/Concepts/FastUserSwitching.html), [AppKit session notification](https://developer.apple.com/documentation/appkit/nsworkspace/sessiondidresignactivenotification)

**High Performance Screen Sharing is a separate feature with important conditions.** It supplies one or two virtual displays and stereo audio; both ends require Apple silicon and macOS Sonoma 14 or newer. Apple permits one High Performance sharing session per Mac, up to 4K per virtual display, and specifies UDP ports 5900–5902 and substantial bandwidth. When authenticated as the user already using the target Mac, it blanks the target's physical displays and prevents local use. This same-user mode directly conflicts with the requested concurrent-use experience. The docs do not establish a complete audio-isolation or automation contract for the different-user case. [Apple: High Performance requirements](https://support.apple.com/guide/remote-desktop/use-high-performance-screen-sharing-apdf8e09f5a9/mac), [Screen Sharing type options](https://support.apple.com/guide/mac-help/screen-sharing-type-options-on-mac-mchl1883115d/mac)

**Spaces organize windows.** Apple documents additional desktops, app assignment, and automatic switching to a Space containing an app's windows. This provides visual organization, not a documented second input/session boundary. An extra physical or software-created display attached to the same session likewise should not be treated as cursor/focus isolation: that conclusion is an architectural inference, not a measured `cctl` result. [Apple: Work in multiple spaces](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)

## Constraints for this toolkit

- **Run the controller inside the selected graphical login session.** This is the recommended architecture, not proof that Cua already supports it. Apple distinguishes HID-level, login-session-level, and application-directed event locations. Audit which locations the pinned Cua build uses, and establish that events stay inside the agent's session. Plain SSH credentials do not prove the process has joined that graphical session. [Apple: CGEventTapLocation](https://developer.apple.com/documentation/coregraphics/cgeventtaplocation), [Fast User Switching/session guidance](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPMultipleUsers/Concepts/FastUserSwitching.html)
- **Permissions still apply.** Accessibility control and screen/system-audio recording are separately permissioned. Provision and verify the controller and media helper in the agent account; do not infer that the human account's grants cover it. Apple does not document this particular Cua/secondary-session combination. [Accessibility](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac), [screen and system-audio recording](https://support.apple.com/guide/mac-help/control-access-screen-system-audio-recording-mchld6aa7d23/mac)
- **Capture is not playback isolation.** ScreenCaptureKit can select displays, applications, windows, and associated audio. Its capture filters do not establish that an app stops playing through the machine's speakers. Likewise, High Performance's stereo-audio transport does not by itself document absence of local playback. Explicitly measure and configure audio routing. [Apple: Meet ScreenCaptureKit](https://developer.apple.com/videos/play/wwdc2022/10156/)
- **Session lifetime matters.** Test connection loss, viewer closure, lock, sleep, user switching, app activation, permissions dialogs, clipboard operations, and whether a remote display still exists afterwards. The cited support docs do not promise a persistent unattended automation session or a public session-provisioning API.
- **A one-Mac setup is not yet verified.** The Apple workflows describe connecting from another Mac. Loopback/same-host viewing, creating an offscreen session without an enduring viewer, third-party VNC compatibility, and driving it from `cctl --host` are separate experiments. Do not imply that adding an account immediately solves them.

## VM option and recommendation

Apple's Virtualization framework and sample app support a macOS guest on Apple silicon, with its own VM configuration, disk, graphical view, keyboard and mouse handling. This is a stronger and more explicit environment boundary than placing windows on another monitor. The toolkit should run in the guest and be reached over its normal transport, rather than controlling the host's VM-viewer window. [Apple: Running macOS in a VM](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)

Audio still needs an explicit choice even with a VM. Apple exposes an output-stream sink that can send guest sound to the host; leaving that sink unset suppresses host playback. This gives a concrete way to keep an emulated sound device while avoiding speaker output, subject to testing guest capture. [Apple: audio output sink](https://developer.apple.com/documentation/virtualization/vzvirtiosounddeviceoutputstreamconfiguration/sink), [VM audio devices](https://developer.apple.com/documentation/virtualization/audio)

**Recommendation:** keep a macOS VM as the clear fallback and prioritize a bounded experiment with a dedicated agent account plus Apple's separate remote desktop. It could retain native application/GPU access with less VM overhead, but that benefit and compatibility are expectations, not measurements. Separate-user native operation should remain experimental until simultaneous human typing and agent clicking, independent capture, and silent host audio pass together. Repeat the acceptance task from at least two harnesses per the project rules. No implementation commitment or new tool-contract fields are needed before that evidence.

## Reuse and project boundary

If this becomes a product, an **optional companion that provisions and manages desktop environments** is a reasonable boundary: it owns session/VM creation, launch, health, viewing, audio routing, and shutdown; `cctl` controls applications inside a chosen ready environment. That is a design recommendation. The same companion could launch arbitrary workloads, so it need not make computer control a dependency.

Reuse existing lifecycle tools before writing a virtualization frontend:

- **Native separate user:** use Apple's Screen Sharing/Remote Desktop services and clients for the feasibility experiment. The unresolved work is reliable provisioning and attachment to that session, especially same-Mac loopback, which the reviewed Apple docs do not establish.
- **VM with a desktop GUI:** UTM supports macOS guests on Apple silicon and exposes lifecycle operations through Shortcuts, AppleScript, and `utmctl`. It explicitly warns that automation does not cover every feature; backend-specific capability checks are needed. [UTM macOS guests](https://docs.getutm.app/guest-support/macos/), [UTM scripting](https://docs.getutm.app/scripting/scripting/)
- **VM with a CLI workflow:** Tart provides macOS/Linux VM creation, cloning, running, configurable resources, directory sharing, and guest IP discovery for SSH. This is a plausible existing lifecycle backend for a companion. Do not assume a headless launch is frictionless: its own FAQ records login-keychain prerequisites on recent macOS. [Tart quick start](https://tart.run/quick-start/), [Tart FAQ](https://tart.run/faq/)

No runtime was installed or evaluated in this research. The recommendation is to wrap a proven backend behind a small environment interface after a successful experiment, rather than move OS provisioning into `cctl` now.
